"Solving" scheduling

A weight-optimization approach to AMDGPU instruction scheduling

01 / 12

The truth about scheduling

Scheduling is impossible to get right. Different kernels want fundamentally different things — one needs maximum occupancy, another needs maximum coexecution. No single policy is optimal everywhere.

The CoExec scheduler was built on this insight: ML kernels care about coexecution, and there is no one scheduler that achieves near-optimal performance across all of them.

But there is a harder problem we have to face: scheduling has side effects. Two schedules with similar register pressure can produce very different register allocation outcomes — one may spill, the other may not. Heuristics that look locally correct can produce globally poor results.

We would thus like a way to teach the scheduler how to schedule for these side effects — to optimize for the final compiled result, not just the intermediate scheduling state.

A new/old approach

Traditional schedulers use a tiered heuristic cascade: check condition A, then B, then C, with rigid priority ordering. The first heuristic that differentiates two candidates wins. The underlying scheduling problem is NP-hard — heuristics are inherently approximate, and the cascade's rigid ordering leaves performance on the table.

The weighted cost approach replaces this with a single scoring function:

Score(candidate) = Σ wi × heuristici(candidate)

Each heuristic returns a numerical cost. Each has an associated weight. The candidate with the highest weighted sum is scheduled next.

The weights are configurable via a JSON file. This transforms the intractable NP scheduling problem into a continuous numerical optimization problem — a domain where highly effective solvers exist.

Optimization problem

θ* = argminθ Σi=1..N PerfEval( schedule(θ, kerneli) )
  • θ is the weight vector — for example, currently 21 weights controlling the scheduling cost model
  • PerfEval evaluates a compiled kernel, currently returning stall percentage from the static simulator
  • The total cost is the sum of stall % across all kernels in the corpus
  • The formulation is extensible — we could weight specific kernels more heavily, or change the metric entirely
06 / 12

Optimization solver

CMA-ES

Covariance Matrix Adaptation Evolution Strategy — a derivative-free optimizer for continuous black-box problems.

  • No gradients needed — the objective (compile N kernels, sum stall %) has no analytic derivative. CMA-ES works from function evaluations alone.
  • Learns variable correlations — adapts a full covariance matrix, discovering that e.g. increasing WStall should coincide with decreasing WMissedSlots
  • Invariant to monotone transformations — we search in log10 space to handle the 16-order-of-magnitude weight range (10−1 to 1015)
  • Robust to noise — population-based sampling averages out per-kernel variance
  • Well-suited to 21 dimensions — CMA-ES is designed for problems with 5–100 parameters
07 / 12

Perf evaluation & kernel corpus

GPUCSim

The static simulator provides cycle-accurate performance estimates at compile time. Each weight vector is evaluated by compiling all 397 kernels and summing their stall percentages — no GPU hardware required.

Full simulation captures spills, va_vdst hazards, and memory pipeline effects that simpler models miss.

MLKernelCorpus

397 production IR files drawn from aiter, triton, gluon, and OAI workloads — intended to be the complete representative set of ML kernels that matter.

Covers FA, GEMM, MoE, and other operator shapes across bf16, fp8, and fp4 dtypes.

Design principles

Pluggable weights

Any user can train weights against their own kernel set. This lets us specialize a delivery for a specific customer, or go back in time and re-optimize against an older compiler.

Side effects are first-class

By optimizing against final compiled output, we directly account for RA spills, va_vdst insertion, and other post-scheduling effects. This contrasts with approaches like MLGO, which relies on rewards based on state observable to the scheduler and cannot capture downstream compilation effects.

Straightforward delivery

A JSON weight vector ships with the compiler. Enable with a flag and point it at the config. No runtime dependencies, no model inference, no rebuilding the compiler.

Maximum solver control

The impacted decision point is pickNode. The weights determine which instruction is scheduled next at every step, giving the solver full control over the schedule.

09 / 12

Best practices

  • Representative corpus — The weighted model is designed to optimize a set of kernels. That set must cover everything we care about scheduling. Missing workloads means unoptimized workloads.
  • Well-designed knobs — Heuristic scores should be smooth and monotonic where possible. A score that jumps discontinuously gives the solver less signal to work with. Orthogonal scores (measuring distinct things) are better than redundant ones.
  • Accurate perf evaluation — The solver is only as good as its feedback. Static simulation accuracy directly translates to real-hardware gains. Garbage in, garbage out.

The solver does not solve all compiler problems — it finds the best compromise given every current deficiency. If a severe RA bug is compensated for by the weights, fixing that bug lets the solver push further. Designing new heuristics which are better fit for the solver, or capture some new scheduling property, gives it increased control.

11 / 12

Known drawbacks

1

Generalization is not guaranteed. The optimized weights are tuned to the corpus. Kernels outside it may not benefit — or could regress. The corpus must be kept representative of real workloads.

2

Accuracy bottleneck. The solver optimizes what the perf tool measures. If the static simulator is inaccurate on a class of kernels, the weights will be mis-tuned for them.

3

Periodic retuning required. Compiler changes (new passes, RA improvements) and new kernel shapes can shift the landscape enough that weights need re-solving.
